# Архитектура MikuOS 0.2

## Системный слой

ESP-IDF 5.5.2 предоставляет драйверы и FreeRTOS. Собственное ядро MikuOS определяет сервисы, состояния, интервалы, IPC, журнал и API, shell вызывает эти операции. Это кооперативная система: короткие шаги сервисов выполняются одним системным worker. Worker обслуживает UART каждые 20 мс и сбрасывает task watchdog с таймаутом 5 секунд. Длительный или блокирующий шаг должен получить отдельный worker/адаптер.

API: `register_service(name, period, enabled, step)`, `set_service`, `post`, `receive`, `log`, `set_telemetry_period`. `step` возвращает true при успехе, false переводит сервис в Faulted. Перезапуск сервиса возвращает его в Ready. При успехе шаг заканчивается в Waiting. Регистрация во время tick и рекурсивный tick запрещены. Сервисные callbacks не должны выбрасывать исключения: ESP-IDF сборка использует стандартные настройки C++ без exceptions.

Реестр ограничен 16 сервисами; FIFO — 32 сообщениями с payload до 4096 байт. `post` сообщает об отказе и увеличивает droppedMessages. Журнал сохраняет 24 укороченные записи. Это не ISR/thread-safe API: все операции ядра исполняются в одном worker. Для будущих асинхронных драйверов необходим безопасный мост к нему.

Встроены telemetry, heartbeat и demo. Телеметрия настраивается 200–10000 мс; heartbeat раз в секунду, demo раз в 5 секунд. Следующий deadline вычисляется от текущего времени, пропущенные шаги не вызывают бесконечный догоняющий цикл.

## Платформа

`Platform` абстрагирует время, память, вывод, перезапуск и конфигурацию. ESP32-S3 реализация использует esp_timer, heap_caps, esp_flash, UART0 GPIO43/44 и NVS. Память разделена на internal и PSRAM. PSRAM включена в octal/80MHz режиме и проверяется при загрузке. Flash Quad/DIO 16 MiB; раздел factory — 4 MiB, storage зарезервирован для будущего хранилища. Автоматического удаления несовместимого NVS нет: ошибка требует отдельной диагностики.

Host/mock использует steady_clock и stdin/stdout. Поток ввода передаёт ограниченные chunks в очередь, main worker обслуживает ядро независимо от ввода. Только main worker обращается к Kernel. Host config хранится в RAM, reboot сбрасывает службы, часы и журнал, сохраняя config. Данные памяти host синтетические. Host слой и C# Simulator имеют разные реализации, но соблюдают одинаковый wire protocol; полной проверки паритета всех команд пока нет.

Текущий аппаратный профиль поддерживает конкретно ESP32-S3 N16R8 через USB-UART. GPIO43/44 явно назначены под UART0. Console runtime отключена; bootloader/ROM могут выдавать строки, которые декодер отбрасывает до LF. Для native USB нужен новый аппаратный адаптер. GPIO/storage, Wi-Fi и BLE должны добавляться отдельными интерфейсами, а не в Kernel.

## ПК

`MikuOS.Core` не зависит от WinForms. Frame/FrameDecoder определяют протокол, ITransport — поток байтов, DeviceSession — ID запросов, ответы, таймауты и счётчики. SimulatorTransport намеренно фрагментирует кадры. Decoder защищён session lock; события обрабатываются на UI thread. UI не использует C++ платформенные вызовы.

MainWindow компонует страницы и маршрутизирует сообщения. Dashboard, SystemMonitor, Terminal и Media — самостоятельные контролы. Settings сохраняет режим/порт в `%APPDATA%/MikuOS/settings.json`, конфигурация платы хранится отдельно в NVS. SerialTransport изолирует System.IO.Ports. Новый TCP-транспорт реализует ITransport; публичное сетевое подключение потребует защиты, которой сейчас нет.

Соединение считается ONLINE при наличии валидных кадров за последние 5 секунд. Открытый порт без кадров имеет CONNECTING/STALE. После исчезновения уже подключённого порта UI повторяет подключение раз в 3 секунды. Изменяющие команды не повторяются автоматически. Read-only снимки tasks/info запрашиваются повторно; состояние задач обновляется раз в 3 секунды. Не все сценарии физического отсоединения проверены аппаратно.

## Media

FFmpeg выдаёт raw RGB в ограниченном размере через stdout. Decoder накапливает полные кадры, ограничивает FPS по монотонным часам, опустошает stderr с ограниченным журналом, при отмене завершает process tree. Каждый экземпляр воспроизведения имеет cancellation и generation, чтобы быстрые переключения не запускали несколько декодеров. Пауза останавливает часы вывода; stdout pipe создаёт обратное давление.

Обычный VideoCanvas копирует RGB в Bitmap и рисует его внутри WinForms с сохранением пропорций; кадр 640×360, максимум 24 FPS. LibVLC отдельно воспроизводит аудио, native video window не используется. В этой версии нет точной синхронизации двух декодеров и перемотки. Видео без звука работает.

ASCII режим: 96×30 / 10 FPS, яркость → символы ` .:-=+*#%@`; масштаб учитывает пропорции символа. Terminal рисует mono/256-color/true-color кадры, Media экспортирует ANSI. Буфер хранит последний кадр, UI не ставит тысячи кадров в очередь. ESP32 отправляет только событие media.ascii.open; видео на плату не передаётся.
